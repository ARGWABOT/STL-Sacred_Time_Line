# The Studio as a project (STL Studio directs itself)

*A procedure of the STL Studio director. The model reads this English version; its Spanish version, `studio-as-project.es.md`, has the same parts and is the one people read and approve. A change is written in both. The inbox (`tools/director/bandeja.ts`) says when to read it: in every review of the project whose repository is the Studio itself.*

## What changes because it is the same repository

STL Studio is also a project of the Studio («STL Studio»): its repository is this same folder, and its development is directed with the STL methodology, like any other, with its diagnosis, its objective, its route and one mission at a time. What changes because it is the same repository:

- **Two kinds of work, kept apart.** The director's work (its `plan.json`, its documents, its answers) goes in the memory of this same repository (branch `stl`, folder `.stl/`) and in «Director (<id>): …» commits, as always. **The work on the product** (`index.html`, `estudio/`, `src/`, `tools/`, `plantilla/`, `docs/metodo/`, `CLAUDE.md`, `AGENTS.md`, `README.md`) is project work: it is executed only with approval in the Studio (an accepted proposal, an answered decision or a delivered mission that authorizes it), in «STL: …» commits with only its paths, and with `npm test` and `npm run typecheck` green. Never mix product work with other projects' data in a commit.
- **What shows, in the README** (accepted proposal «Lo que se sube, limpio y firmado desde el commit», point 5): a product change that shows (something new or different on screen, in a command or in how it is installed) takes its line to the README in the same commit, so the README never contradicts the product.
- **What the owner asks about the Studio in this session** counts as if they had left it in the Inbox: the director executes it, and in the next review of the STL project records it in its history (`resumen.avanzamos` and, if it counts for a future phase, `adelantado`), so the product's progress shows in the Studio and not only in the chat.
- **What the owner asks about the Studio is for always and for everyone.** Their notes on how the Studio works or how the director works (a rule, a behavior, a way of running the flow) are not instructions for today's review: they go into the product (`CLAUDE.md`, `AGENTS.md`, `docs/metodo/`, the launcher's assignment or the code), so they hold in every review and for everyone who installs the Studio, and the answer says where it went. If one clashes with the method or with another rule, it is raised as a decision before writing it. **Nothing stays in a session's context** (the owner's voice note of 22 October 2026: the model remembers nothing from one session to the next): what the code can check goes in the code, with its test and, if it is a director rule, with its check in `validarPlan` or in `bandeja.ts --listo`; the prose of the rules alone is not enough, because it is read in every session but nothing prevents skipping it. And a new rule is crossed with the existing ones, with a case that joins them in its test: two rules that silently contradict each other are the hardest failure to see (the reserve counted the missions that the closing rule held back, and the owner was left without a mission).
- **The fronts** name only the product's code and documents: their `rutas` never include `.stl/` or `proyectos/` (the projects' memory is not the Studio's work, and this way it does not pollute the effort).
- **The diagnosis** starts from what is already written about the product: `docs/metodo/evaluacion-studio.md` (the priorities towards a publishable and replicable product), `docs/metodo/diseno-studio.md` (the design and its pending decisions) and the STL Methodology. The owner wants to publish it as a free product for developers: clone it on another computer, hand it projects and work with the method.
- **Everything is project-agnostic** (the owner's rule, 21 October 2026): the Studio is the layer between whoever directs and the model, to manage any kind of project. Every function, design, optimization or critical rule made in the Studio or in the director is thought for any project someone hands it (software, a thesis, a site, a product), never only for this one; STL Studio is only the first, the pilot that tests it. If something only serves this project, it goes in its memory, not in the product.
- **Care with the core**: a change to the Studio affects every project. Before closing product work, run the audit of what it touched: tests and types, always. Look at it in the browser only when asked or needed (CLAUDE.md › «Mirar en pantalla»). **And a change to what guides the director** (its rules, its procedures, the launcher's assignment or the inbox) is guarded with the fixed cases (`src/director/casosFijos.ts`, their situations in `src/director/medicion.ts`): what the code can check goes in the code, with its test, and every closing checks it for free (`validarPlan`, `bandeja.ts --listo`). The run with the real director is requested by the person, whenever they want, with its cost in view, with «Medir el núcleo» (`{ "vista": "modelo", "ancla": "m-medicion" }`), and never goes inside a review; the inbox says how the last one went. **What already passes is not run again, and the measurement does not hold your queue** (the owner's voice notes nmvrimph5tit and nmvsgcn7otit, 28 October 2026: «I don't want us to keep skidding on tests that are too long»): a change goes in with its tests and types green, and the queue goes on; when requesting it, the person picks one by one which of the failing cases to measure, to see whether a change fixed them, or all of them, only for a new baseline (when changing model or effort). Ask for it only when a change wants to fix a failing case, and the mission says which one to check. Each new director error the person points out is added as a case, in its group, with its situation and its test (accepted proposal pr_nucleo_medido).
